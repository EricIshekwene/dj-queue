# DJ Queue — Round 2 decisions

Eric delegated every round-2 decision ("make a good decision"). One line each + why. Sections per agent.

## R2-CORE (core library, `djq`, metadata)

- **Edits store only overrides.** `Edit` fields are optional (nil = follow `Settings.defaults`); `aspect`/`coverIncludesText` are stored as `aspectOverride`/`coverIncludesTextOverride` under the same JSON keys. Why: north star #10; keeping the JSON keys makes the migration a value rewrite, not a format change.
- **Migration v2 rewrites only values equal to the round-1 hard defaults** (aspect 9:16, cover includes text = true) to "follow default"; every other value (crop, trims, cover time, a `false` cover-text) stays. Why: round 1 always wrote those two, so they were never Eric's choice, and the seeded defaults are identical — the resolved edit is unchanged (tested on a copy of the real backup).
- **A file DB is copied to `<app support>/backups/queue-before-schema2-*.sqlite` before migrating.** Why: cheap insurance for Eric's live scores.
- **Round-1 settings keys (`defaultStyle`, `defaultTextSize`, `defaultPosY`, `defaultCaptionTemplateId`, `defaultHashtagSetIds`) seed `Settings.defaults` when it is missing**, and stay available as deprecated forwarding properties. Why: lossless + the round-1 app keeps compiling.
- **Crop must still be confirmed per clip.** The default crop anchor only drives previews/thumbnails/proxies; `Make ready with defaults` confirms it (writes the rect). Why: framing is the one thing that can't be checked without looking; it keeps the 62 real clips in "needs edit" until Eric acts.
- **Heads-up for Eric: after installing, clips can become Ready without being opened again.** Example: the one clip already edited in round 1 (crop + text set) turns Ready at the first intake, because its caption now comes from the default caption template. Ready clips can be auto-drafted into proposed weeks (drafts still need approval). This is intended: the defaults count. Don't run a round-1 build against the migrated database (it would rewrite edits with explicit 9:16 and drop the New clip defaults when saving Settings).
- **Text/caption readiness uses resolved values.** A clip whose text resolves from its Title (or "No text" for Talking) and whose caption resolves from an existing template has no text/caption issue; no explicit v1 is needed. Why: "clips store only overrides" — requiring explicit copies of defaults would contradict it.
- **Default text source = Title; with no title the text is empty (issue "Add text (no title yet)")** — never the tidied tag. Options: Title / raw tag verbatim / empty. Why: no in-app intelligence (#9).
- **Caption/YouTube `{text}` = overlay text, else Title, else raw tag verbatim.** Why: north star #9.
- **Over-limit captions stay over-limit;** `ValidationIssue` carries `count`/`limit`/`countWithoutHashtags`, and `Captions.withoutHashtags` is the explicit "Drop hashtags for X" (writes a per-platform caption override). Why: no silent changes (#9).
- **Rotating per-video hashtag sub-sets removed;** `Captions.hashtags(videoId:)` keeps the parameter but ignores it. Why: #9; parameter kept for app compile.
- **Prefill left the app.** The formatter is `scripts/prefill_titles.py` (stdlib, same rules, writes `title_suggestions` with source `prefill_titles.py`, confidence 0.3); `djq prefill` removed. `Prefill`/`PrefillRules` stay only as a deprecated shim (no core caller) so the round-1 app compiles. Why: #9; a shim avoids editing UI-owned files mid-rebuild.
- **Default trim = markers ± extra seconds (default 0/0); clips without markers use the whole file.** The render hash follows the resolved trim, so existing renders re-render once. Why: north star #5 (expected re-render).
- **Default kind applies to new clips at intake; `content-type: talking` still wins.** Why: manifest data beats a default.
- **Platforms default:** `defaults.platforms` (all six) + per-clip `skippedPlatforms` / `includedPlatforms`. Why: lets a default leave a platform out while a clip can opt in.
- **Safe-zone default platforms = TikTok + Instagram.** Why: the two most cropped-by-UI feeds; the editor can add more.
- **Resolved types encode deterministically (sets sorted).** Why: stable hashes and batch snapshots.
- **Manifest `title` seeds only a title that was never set.** Clearing a title (app, `djq title --clear`, bulk) leaves a tombstone (`title_source = "cleared"`), so intake never brings it back; when the app title is set or cleared, a different manifest title is offered as a suggestion (source `videos.json title`) instead. Manifest `title_suggestions` are re-synced every intake (origin "manifest", compared after dropping empty/duplicate entries so identical lists aren't rewritten); `djq suggest` ones (origin "agent") are kept; same text+source updates in place. Malformed suggestions are ignored. Why: Eric's choice — including "no title" — always wins (review fix).
- **Bulk actions run in one transaction with a journal row holding before/after snapshots** (clip fields, edit, versions; whole plan tables for plan actions; render retire flags for re-render). Undo skips clips changed since (and refuses the plan part if slots/weeks changed, a post was added, or a post was marked posted/failed since) unless `force`. Why: one ⌘Z per batch that can never overwrite later work.
- **A partial undo leaves the batch open.** Clips skipped as "changed again" stay pending; the journal records which clips (and the plan part) were restored, a later undo — usually with `force` — restores only the rest, and the batch is marked undone only when nothing remains. Why: `force` must be able to finish what the first undo skipped (review fix).
- **Dry run = run the action and roll the transaction back.** Why: the preview is exactly what would happen.
- **"Apply defaults" touches v1 only** (later versions keep their own text). Frame re-fits the crop to the default anchor. Why: v2+ exist for reposts with deliberately different text.
- **`setCaptionTemplate` clears a written v1 caption**, otherwise the template would have no effect. Why: the action must do what its label says (undoable).
- **Bulk post-today follows the planner's rule** (pinned/full today → that clip is skipped with the reason). Why: no special-case planning in bulk.
- **Re-render retires the clip's render rows (files stay until replaced); the engine re-renders on its next tick.** Why: reuses the normal render path; undo can un-retire while files exist.
- **Proxies: 540 px wide (540×960 for 9:16), H.264 + AAC 96k (tiles can unmute), confirmed crop else the default anchor crop, keyed by video/fingerprint/crop/aspect/range; range = trim (default) or whole file; one proxy kept per clip+range; no text overlay.** Why: cheap autoplay that matches what will post; the UI overlays text itself.
- **Proxies are encoded only on `ProxyService`'s own serial background queue**; the engine's "proxies" step just enqueues missing proxies at background priority (clips to score first) and returns, is skipped while a render ran/waits, and background jobs pause while a render runs. Each encode has a 120 s ffmpeg timeout per attempt and holds a per-clip+range `flock` so the app and engine/CLI never encode the same proxy (the second waits and reuses the file). A failed background proxy isn't retried until its key changes; visible (UI) requests always try. On by default only with the real `Renderer` (`Engine.proxyService`, shareable with the UI). Why: proxies can never delay missed/due/alerts/render (review fix).
- **PlatformUI values = DESIGN-v2 §8 measurements**, stored once in `PlatformUI.table` with both screen (9:19.5 phone) and frame (9:16 video) rects; 4:5/1:1 overlays are clipped by mapping the frame rects onto a centred picture; cards (Threads, X) cover nothing; X crops portrait video to 4:5. Caption preview: TikTok 2 lines + "… more", IG 1 line + "…", FB 1 line + "… more", Shorts title 1 line + "…", Threads/X 5 lines + "Show more".
- **Ask-an-agent prompts are pure templates** (`AgentPrompts.titles`), a clip needs help when it has no title and no suggestion ≥ 0.6. The prompt's JSON example is the exact `djq suggest --file` format (round-trip tested). Why: Eric's own agent does the thinking, the app stays dumb.
- **Agent JSON (`AgentAPI`) uses snake_case keys and only ever grows.** Why: stable contract for outside agents.
- **The real-backup migration test runs only with `DJQ_MIGRATION_BACKUP=<path>`** (it copies the file and checksums the original); a synthetic v1 test always runs. Why: the repo is public — no private paths in tests.
- **"Make ready with defaults" reports where every clip ends up** (`BulkResult.outlook`: ready · still need a title · other issues), and when clips still need a title the sheet offers two explicit choices: **Ask an agent for these M** (copies `AgentPrompts.titles`) or **Use raw tag as title for these M** (`BulkActions.useRawTagAsTitle` / `djq bulk title-raw-tag`: the tag verbatim, one undoable batch). Why: the old "Updated 3 clips" claimed success while nothing became ready; the app still never invents a title.
- **Toasts centre on the content area and stack above floating controls** (bulk bar, Score pill) via one `DSToastLayoutKey` preference; an applied bulk action clears the selection unless it changed nothing. Why: the 6 s toast covered the bulk bar and the Score pill (final review defect 1).

## R3-UNQUEUE — Remove from queue, Send to queue, stage moves (F1 + F6)

- **"Remove from queue" = an app-owned flag `videos.held_in_edit` (schema v3, additive column, default 0; a file DB is copied to `backups/queue-before-schema3-*` first).** While held, `computeState` returns `needs_edit` (after missing/excluded, before posts) and `Validation.issues` leads with "Sent back from Queue — Send to queue when it's ready". Why: forcing Edit through the normal state/validation path means the planner, Queue, Edit list, filters and agents all see it with no special cases.
- **Removal follows `Planner.remove` per slot, no backfill:** every slot of the clip from today on with nothing posted is cleared like `remove(slotId:)` (a pinned slot goes with its pin), plus a past slot that only held in-flight posts; slots with a posted post stay. Other clips keep their days. Why: Eric asked for "back to Edit", not a re-plan; reshuffling would move clips he already approved.
- **Every in-flight post of a held clip is deleted (planned/rendering/rendered/due/overdue — retries and reposts too); posted/failed/skipped posts and post history stay.** Why: nothing of a clip Eric pulled back may post; terminal posts are history.
- **Undo is the bulk journal:** `ClipSnap` gained `held` (nil = not held, so pre-v3 journals still compare equal) and the action snapshots the plan, so one undo restores flag, slots, weeks and posts exactly (tested field by field).
- **Remove from queue asks first when it would remove scheduled days, even for one clip,** listing them from the dry run ("Tue 3 Nov · 6 platforms · pinned"); otherwise one clip applies at once with "Removed from queue · Undo". Why: removing approved days is the one irreversible-looking part; the list makes it concrete.
- **Unscored and excluded clips are skipped by Remove from queue** ("isn't in the queue"). Why: holding them would surprise later (a clip scored next week would land in Edit for no visible reason).
- **Stage model (F6): Score (no score) → Edit (needs edit or held) → Queue (ready; a day in a proposed/draft week still counts) → Scheduled (approved week, not finished) → Posted.** `ClipStage.of(video)` is pure; long-form/excluded/missing clips have no stage. Why: matches the sidebar pipeline and the stored state, so no new state to keep in sync.
- **Back moves:** Edit → Score clears the score (always confirms "Clear score 42 and send back to Score?"; the held flag is kept, so a re-scored held clip returns to Edit) · Queue → Edit is Remove from queue · Scheduled → Queue unplans without the flag (stays ready) and is refused once any platform posted ("skip or reset its posts in Posts") · Posted has no back (Repost / Reset instead).
- **Forward moves:** Score → opens Score (a score is Eric's input, never invented) · Edit → Queue clears the flag and runs make-ready's crop step; still-invalid clips stay in Edit and the note/toast/sheet say exactly what's missing (no change at all → reported as skipped with that reason) · Queue → Scheduled pins to the next open day of this or next week via `Planner.pin` (same as "Add to week"; a draft week is reported as "needs approval in Week") · Scheduled → Posted only through Today's Mark posted (the control opens it for the next post).
- **One control everywhere:** `StageControl` = ghost "‹ Back to …" + outlined "… ›" (never a primary), tooltips name exactly what happens, disabled with the reason; compact icon pair on list rows and Week cards (on hover), media buttons on grid tiles, full labels on Cards/Single and in the editor header; the same items in ⋯/context menus (Queue, Edit, Week, Library via the shared clip menu), ⌘K (per clip + selection) and the Queue/Edit bulk bars (More). Score cards don't get it: Score's own score field is the forward control and there is no back.
- **On Queue, "Remove from queue" (→ Edit) is offered for every clip (planned ones too), and the stage back for a planned clip reads "Back to Queue" (unschedule).** Why: Eric's F1 wording stays the Queue's own action; the stage control stays literal about the one-step move.
- **Edit cards: "Open editor" became a ghost button** so "Send to queue ›" is the single outlined action on the card. Why: one emphasised action per card.
- **Library pill "Sent back to Edit"** (warning, ↩ icon) for held clips; the Edit filter chip "Sent back from Queue" sorts first.
- **CLI:** `djq unqueue|requeue <ids…>`, `djq stage <ids…> [back|forward]` (no direction = show stage + what each move would do or why not), all `--dry-run`/`--json`; `djq bulk unqueue|requeue` for `--filter`. `requeue` only clears the flag (agents); the app's "Send to queue" is the stage forward (flag + crop). Why: agents get the minimal, predictable operation; Eric's button does the helpful whole step.
- **Review fix: a clip that already posted anywhere can't be removed from the queue** (posted regular/retry post, or state posting/posted/partial). `removeFromQueue` skips it with the same reason as the stage back ("Already posted on TikTok — it can't leave the plan; skip or reset its posts in Posts"), the Queue/Week/⌘K items and bulk bar are disabled with it when no target can go, and `djq unqueue` prints it per clip. The held flag also never masks a posted state (`Store.isHeld`: held counts only with nothing posted). Why: otherwise the other platforms silently never post and the clip shows as Posted.
- **Review fix: with Autoplay off, hovering does nothing** (no play, no sound): every preview reads `PlaybackPrefs.hoverSound = autoplay && unmuteOnHover`. Why: Settings already disables "Unmute on hover" while Autoplay is off; behaviour now matches what the control says.
- **Snapshots of native menus are drawn by `SnapshotMenuMock`** (same items, tooltips shown under each) because AppKit menus aren't in the window capture.

## R3-FIXES — Posts cards, paused status, hover sound

- **"Unmute on hover" defaults on; `PlaybackPrefs` moved to DJQCore with a lenient decoder.** Saved prefs without `unmuteOnHoverChosen` (every pre-round-3 save — Eric never chose "off", it was the old default) load as on; the Settings switch marks the choice so it sticks afterwards. Why: Eric wants sound on hover, and the migration must be unit-testable (the app target has no tests).
- **Hovering a clip card (not only its picture) plays it with sound**, starting playback with a priority slot when it wasn't playing (focus-only, or 4 others playing), and mutes on exit; `DSPlaybackBudget.effectiveAudible` lets the hovered clip win over a button-unmuted one so exactly one clip is heard; the mute button while hovering mutes until the pointer leaves. Why: before, sound needed the preview itself to be playing *and* the pointer exactly on the thumbnail.
- **"Posting paused" card only on Posts;** everywhere else the sidebar status reads "⏸ Posting paused" in amber (tinted row) and is the control: Resume posting / Pause posting… (confirms, same dialog as before) / Pause one platform ▸. Partial pauses read "Running · TikTok paused". Problem, engine and runway cards unchanged. Why: Eric's request; one quiet indicator instead of a banner on every screen.
- **Posts = one DSCard per (clip, scheduled day)** (`PostGrouping` in DJQCore, tested): cover, title + session, "Sun 2 Nov · 12:30–7:00 PM", a status summary ("6 platforms · all ready" / "2 posted · 1 failed · 1 due now", "+ 1 retry"), state-coloured platform chips (glyph + short name, tooltip with state and time); the chevron "Show platforms" opens per-platform rows (time only — the card has the day; "Posted <date>" for posted rows; v/# only when ≠ v1/#1; Retry/Repost label; pill; link; right-click actions; click → inspector). Why: Eric saw the same clip six times in a row.
- **Groups use the scheduled day for every tab, rows sort by time then platform; a retry/repost on another day is its own card, on the same day it folds in with a label.** Why: the slot is what Eric thinks in; posted time still shows on the row.
- **Problems tab: cards always open with the affected platforms as the existing problem cards (all fixes kept, no repeated clip name) and the rest folded into "+N fine" (with their glyphs).** Why: fixes stay one click away; the fine platforms give context without noise.
- **Card checkbox selects all the card's posts; bulk Reset/Skip/Retry and ⇧/⌘ selection still work per post.** Expanded / "+N fine" state lives in `PostsCardState` for the app session only. Why: keeps the existing post-level bulk actions; session memory as asked.
- **Grids play on hover only (Settings → "Grids: play on hover only", default on, same chosen-flag migration).** Off-hover grid tiles show their cover; on hover the tile plays (with sound when Unmute on hover is on); on exit the player is released and the cover comes back (not paused at a frame — frees the decoder and matches the still grid). The Score grid's keyboard-focused tile counts as hovered. Cards/List follow the autoplay setting, Single keeps focus playback. `PreviewPlayback.plays` / `proxyTargets` are pure and tested. Why: a grid of 20 moving tiles is noise; one at a time under the pointer is calm.
- **Grid proxies: the hovered tile at visible priority + its two neighbours in display order prefetched at background priority (nothing hovered: the two tiles at the middle of what's visible).** Why: cheap approximation of "nearest the pointer / viewport centre" with no geometry tracking; posters cover the wait.
