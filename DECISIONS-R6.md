# DJ Queue round 6 — decisions (Postiz publisher)

Routine decisions made while building, one line each with the why. Session-level decisions (one request per platform
post, API key in the Keychain, 25 calls/hour, replace instead of edit, reconcile in the tick, no per-clip overrides,
Facebook keeps 90 s, one v0.7.0 ship) are in the session record and docs/postiz.md.

## Core (agent/r6-core)

1. **Settings → `publishing` decodes field by field and never fails.** Each field falls back to its own default (string-keyed maps, unknown platforms/values dropped), so a hand-edited or older row can never send Eric's whole Settings back to defaults.
2. **Limits carry a revision (`Settings.limitsRevision`, 2).** A row without it is revision 1: a field moves to the new default only when it still equals the old default (TikTok caption 4000 → 2200, TikTok title — → 90, Instagram 4 GB → 300 MB); Eric's own values stay, and once saved at revision 2 an explicit 4000 is never "migrated" again. Migration is in memory until the next save.
3. **TikTok title limit 90 is a real `PlatformLimits` default now.** It only feeds the Postiz payload and the title notice; nothing else read TikTok's `titleLimit` before.
4. **Long YouTube/TikTok titles: a non-blocking notice, not a new blocking issue kind.** `Validation.titleChecks` / `TitleCheck` says when the template title had to be shortened (the editor shows it); the payload clamps at 100 / 90. A new blocking kind would move Queue/Scheduled clips to Edit at install. An explicit YouTube title over the limit still blocks (`.titleTooLong`), as before.
5. **F5: past draft-week days with no posts are dropped, pinned ones too.** A pin on a day that passed without approval can't post, and keeping it hides the clip from the Queue for good; approved weeks and slots with any post are never touched. `Queue.ordered()` ignores such slots even before the plan step deletes them.
6. **Key save through `security -i` with the command on stdin.** The key never appears in a process argument list; the item is created by `/usr/bin/security`, which therefore stays trusted, so reads after every rebuild don't prompt. The key must be one token (letters, digits, `-_.:+/=`), which also keeps the `security -i` line unambiguous.
7. **`PostizLive.disabled` kill switch, and no test ever holds the real Keychain store.** Tests (Fixture) and `DJQ_POSTIZ_OFFLINE=1` turn off the real transport and the real `/usr/bin/security`; every test injects a fake transport and a recording `security` runner (M1 review #2), so nothing in `swift test` can reach Postiz or Eric's Keychain item.
8. **One open job per post is a unique partial index** (`post_id` where `closed_at IS NULL`). A job being replaced stays open (`deleting`) until Postiz answered OK/404, so "no create after a failed delete" holds structurally, across processes.
9. **Final vs non-final close reasons.** Published, inbox, error, copyright, vanished and rejected end Postiz delivery for that post (never resubmitted by itself); replaced, cancelled and interrupted don't. `PostActions.reset` releases error/rejected/vanished/interrupted only — never published/inbox/copyright.
10. **The engine gets Postiz by default.** `Engine.init` builds a live `PostizService` when none is passed, so the app and `djq tick` need no code change; with every platform on Manual (the default) it reads no Keychain and makes no call.
11. **No manual "due" notification for a post Postiz will deliver** — one with an open job, or routed to Postiz with no final job (its render may land after the slot and it's submitted then). The router's fallback reasons (no key, bad key, no/disabled channel) still notify as Manual.
12. **Budget reserves.** Creates leave one call per hour for sync; analytics leaves eight. Uploads count as calls (a create needs up to three).
13. **403 counts as "key refused"** (wrong organization means the key doesn't belong to this Postiz).
14. **An interrupted create** (network/5xx after the create was sent) keeps its claim; the sync step adopts the Postiz post with the same channel and date, or releases the claim after 10 minutes. Errors before the create was sent release it at once.
15. **YouTube `tags` as `[{value, label}]` and `thumbnail` as `{id, path}`**, the Postiz DTO shapes (not seen live; a 400 would fall back to Today with Postiz's message).
16. **Test-mode TikTok PUBLISHED closes the job as "inbox"** and the post goes back to Manual with a notification ("finish it in the app, then Mark posted"); it is never resubmitted.
17. **A cancelled job sets the post's `publisher` back to "manual"**; the `publisher` column always says who delivers the post now.
18. **Marked posted by hand while Postiz still holds it → the Postiz copy is deleted** (unless Postiz already published it), so it never posts twice.
19. **Near the slot: never replace, cancel only after a fresh look** (M2 review #6, #9). From 5 min before the slot an edit/re-render/re-plan leaves Postiz's copy as it is (logged once); a cancel first reads the post's state with one `GET /posts` in the same step (published → recorded, never deleted).
20. **Approving a week mid-week drops its passed draft days first** (M1 review #9), the same rule as the plan step, so their clips never read "Scheduled" in an approved week without posts.
21. **Transport hardening (M1 review #7):** `apiBase` must be https (otherwise the cloud base is used), redirects are never followed (the key would follow them), stale upload temp files are swept, and `hourlyBudget` is at least 10 so the reserves can't starve creates.
22. **Keychain read: only exit 44 means "no key"** (M1 review #8); a locked or refused Keychain is an error, so Eric isn't told to re-paste a key that is fine.
23. **`final` is written only when a job closes or is released** (M1 review #4), so a later save of the row never undoes a reset.
24. **A wrong-typed top-level `publishing` or `limitsRevision` is dropped before decoding** (M1 review #5): that field takes its default, everything else in Settings is kept.
25. **Doctor's Postiz checks live in `Doctor.swift` (CLI branch)**; the core `PostizDoctor` draft was removed so there is one set of checks. Core keeps the helpers they read (`stuckJobs`, `linkMissingPosts`, `deliversThroughPostiz`, the jobs/budget Store API) and the `syncNowKey` that `requestSync()` sets. Doctor should also report `postiz.create_unknown` (`PostizJob.isUnconfirmed`: phase `creating` with remote state `UNCONFIRMED`; no new phase, so existing switches keep compiling).
26. **`djq postiz test --draft` records** are `kind = "test"` rows, closed at once (`test_draft`); reconciliation never touches them.
27. **Analytics parsing:** a never-decreasing series reads as cumulative (last value), anything else as daily counts (sum); an unknown shape stores nothing and is logged once.
28. **The reconcile loop decides from the database every tick** (no hooks in planner paths): every path that removes, moves or re-states a post (planner remove/unplan/move/swap/push/rebuild/skip-next, reflow from missed, skip/reset/fixed/repost, bulk unqueue + undo, revalidation, settings) is covered by a test plus a seeded fuzz with failing deletes and creates.
29. **Never-double-post is per lineage (clip + platform), not per post id** (M2 review #1): planner moves re-create posts under new ids, so a new job waits until every other job of the clip on that platform is confirmed gone, and never follows a published one (the new post is recorded posted with that link instead). Checked inside the claim transaction.
30. **A sent create is closed only on a definite answer** (M2 review #2): 400/413 → rejected, 401/429 → released; anything else keeps the claim, the sync step adopts the single matching Postiz post, and if none shows up the job is marked unconfirmed (`isUnconfirmed`) — loud, Doctor `postiz.create_unknown`, nothing re-sent until Eric checks (`resolveUnknown`). `submittedAt` is written before the create so a crash before sending is told apart and simply released.
31. **One "settings allow Postiz" predicate for cancel and create** (M2 review #3): global pause, platform off, platform paused, Manual.
32. **Handed to Today stays Manual** (M2 review #4): once the manual "due" notice for a post went out, it is never auto-sent to Postiz later.
33. **Test mode is frozen per job** (M2 review #5): docs §6 holds — switching it changes only new submissions.
34. **A closed job is never reopened by a stale save; the first close wins** (M2 review #7).
35. **Adoption needs a single match** (channel + date ±60 s, not held by another job; past slots rounded up to a minute) (M2 review #8); an ambiguous match is treated as not found.
36. **No key saved → no call and no budget slot** (CLI need #2): `PostizService.call` checks the key's presence before taking budget.
37. **An undo never goes live silently** (CLI review M1): `BulkActions.undo` refuses when restoring a settings snapshot would put platforms with waiting posts back on Postiz with test run off; `undoWouldGoLive(_:)` previews it and `undo(_:force:dryRun:confirmGoLive: true)` does it. The old `undo(_:force:dryRun:)` (and the app's ⌘Z queue) keep compiling and get the refusal with its reason.
38. **Unconfirmed creates are a remote-state marker, not a new phase** (`PostizJob.isUnconfirmed`: `creating` + `UNCONFIRMED`), so the UI's exhaustive `switch` on `PostizJobPhase` keeps compiling.
39. **A test-run TikTok in the TikTok inbox is never "missed"** (UI need #3): `missed()` skips it, so it stays out of Problems; it shows as "In TikTok inbox" until Eric marks it posted.
40. **One display state for every screen** (UI need #2): `PostizService.displayState(for:)` / the pure `PostizDisplayState.of(post:job:route:handedToToday:now:)` mirror UI decision #10, plus "Check Postiz" for an unconfirmed create, a re-planned post Postiz still holds as its earlier copy, and "already on Today" for a post handed to Today.
41. **Scratch homes are offline by default** (UI review H3): with `DJQ_HOME` or `DJQ_ROOT` set (dev runs, the auto-update gate, `djq` in a dev root) the real Keychain and live Postiz are off unless `DJQ_POSTIZ_LIVE=1`; `DJQ_POSTIZ_OFFLINE=1` still wins. Applies to the app and `djq` alike (`PostizLive`).
42. **Adoption is exact** (re-review N1): an unconfirmed create is matched only to the one Postiz post with its channel, the exact date sent and the exact caption (`PostizJob.content`); two open jobs on one channel never share a minute (+1 min each). Zero or several matches stay unconfirmed; `resolveUnknown` adopts on exactly one match and otherwise throws — it never re-sends.
43. **Eric resolves an unconfirmed create offline** (re-review N3): `PostizService.resolveUnconfirmed(postId:inPostiz:)` — `true` closes it as Postiz's (posted, link later via `djq postiz link`, never sent again), `false` puts it on Today (final; Postiz again only after a reset). No key or call needed. Notified daily while unresolved; when the platform no longer routes to Postiz the post reaches Today with a critical "check the Postiz calendar first" notice instead of wedging. Errors that mean "never sent" (no internet, host not found, can't connect, DNS) are `PostizError.notSent` and release the claim at once.
44. **Handed to Today is sticky** (re-review N2): decided from the post's history (a manual due / post now / missed / shift plan) since its last reset, not from its current state; a render of a `due` post keeps it `due`.
45. **A cancel near the slot always sends the DELETE** (re-review N4), even when `GET /posts` doesn't list the post (a 404 counts as done); the sync step never closes a deleting job on absence alone.
46. **A test-run draft an hour past its slot is notified** (re-review N5): release it or post it by hand.
47. **`DJQ_HOME` / `DJQ_ROOT` set at all (even empty) = scratch** (re-review N6), exactly as `Paths.standard` reads them.
48. **Resolve never races a create** (round 3, R3-1): both `resolveUnknown` and `resolveUnconfirmed` refuse unless the job is unconfirmed ("still in flight — wait for the next check"); a create that lands after its job was closed by anyone else is deleted from Postiz at once (or tracked as a new `deleting` job that blocks the clip + platform until the DELETE succeeds) — never Postiz and Today both.

## CLI (agent/r6-cli)

1. **Doctor's Postiz checks live in `Doctor.swift`, not core's `PostizDoctor.findings`.** The brief fixes severities that differ from core's (stuck and channel_disabled are errors, link_missing a warning) and adds rate_limited, fallback and test_mode; one implementation in the file Doctor owns avoids two diverging lists. Core's `PostizDoctor` is unused now (see CLI-NEEDS). They pass as one group, `postiz`.
2. **Every platform Manual → one info, "Postiz not in use", and no Keychain question.** That's Eric's installed state today, so Doctor stays clean and no `security` process runs (tests never touch the Keychain either).
3. **`postiz.mapping_missing` is a warning, an error when that platform has posts in the next 48 h** (they'll go to Today). A mapped channel that vanished from Postiz's list counts as missing.
4. **`postiz.delete_pending` kept** (core's id): a post DJ Queue can't remove from Postiz after 3 tries is worth a warning.
5. **`postiz.fallback` looks 7 days ahead** and gives each post's reason: Postiz refused it, it was deleted in Postiz, a test-run TikTok in the inbox, or the route's reason (no key, no channel, disabled).
6. **`djq doctor --live` is one `GET /integrations`, only when a key is saved.** It refreshes the channel cache and the key flag; a refused key shows as key_invalid at once, no answer as a not_connected warning. Plain `doctor` stays offline and read-only.
7. **Settings changes go through `BulkActions.record(settings: true)`** (undo with `djq bulk undo <batch>`) and log one "Settings → Publishing changed from djq" event.
8. **`--yes` is needed only when a change makes approved posts go out for real**: a platform to Postiz with a channel, a new channel on a Postiz platform, or test run off, for enabled platforms. Mapping while Manual, test run on and back to Manual never need it. Without it nothing changes and the exit code is 1.
9. **`djq postiz test` never schedules real posts, even with `--yes`.** A real test post would bypass DJ Queue's tracking (no job, no link back, double-post risk with the week); real posts go out only from an approved week. No flag → refused, pick `--dry-run` or `--draft`.
10. **`status` makes one live check when a key is saved.** Exit 0 only when connected and all six channels are mapped to current, enabled channels; otherwise 2 with the reasons listed (3 with `--offline`, see 20). Without a key no call is made (no budget slot spent).
11. **Channel ids appear only with `--ids`**, also in `test` bodies (`<channel id>`), so output pasted into chat or Notion carries names and providers only.
12. **Auto-map uses exact provider identifiers** and keeps a mapping that is still valid. Two channels with the same provider (a second account) or none are left for Eric with a hint; `map <platform> "<name>"` picks by name and refuses a channel of another platform (e.g. Instagram-via-Facebook for Instagram is allowed with a note, X for Instagram is refused).
13. **A failed live channel list falls back to the cached one with a note** (map and channels), so offline work and dry runs still show what would change.
14. **Caption limits are cached a day per channel** (kv `postiz.captionLimits`) and fetched only for channels of DJ platforms: six calls once, not every `djq postiz channels`.
15. **`postiz sync` doesn't race the app's engine**: when DJ Queue holds the engine lock it sets the sync-now flag and posts ChangeSignal (as `djq tick` does); `--force` syncs here.
16. **Added `djq postiz release <post> --yes`** for releasing a test-run draft (core's `releaseDraft`), guarded like the other real-post switches.
17. **The CLI tests run the built `djq`** against a throwaway file database with `DJQ_POSTIZ_OFFLINE=1`; it is found next to the test bundle (so `--scratch-path` works).
18. **Two small `PostizService` helpers (`captionLimits`, `requestSync`) sit in `Doctor.swift`**: the CLI module can't reach the service's internal budgeted call path, and Doctor.swift is the core file this branch owns. Core may move them.
19. **`djq bulk undo` checks Postiz going live** (review M1): the undo runs in a savepoint, Settings → Publishing before and after are compared with the same go-live rule, and it's rolled back with exit 2 unless `--yes`. The core-level guard in `BulkActions.undo` is core's.
20. **`status --offline` exits 3, never 0** (review L6): without a check, "ready" can't be claimed.
21. **`DJQ_NO_SIGNAL=1` turns off the CLI's ChangeSignal** (review L5), so tests that run `djq` never make the installed app reload or tick.
22. **`djq bulk undo` uses core's `undoWouldGoLive` + `undo(confirmGoLive:)`** (replaces the savepoint check): same `--yes` UX, exit 2 when refused; core counts only platforms with posts waiting, so an undo with nothing to send isn't blocked.
23. **`postiz.create_unknown` (error) and `djq postiz resolve`** (see 25): a create with no answer blocks new sends for that post until Eric checks the Postiz calendar; `resolve` settles it (see 25). No `--yes`: it never creates anything itself.
24. **Test-mode notes follow core's "test mode is frozen per job"**: switching it changes only posts sent from then on; `test-mode off` still needs `--yes` because those go out for real.
25. **`djq postiz resolve <post>` never guesses**: plain `resolve` is one live look that adopts only core's exact single match, else exit 2 with both choices; `--in-postiz` / `--not-in-postiz` record Eric's answer offline (no key, no call). No `--yes`: Eric checked the calendar, and neither path sends anything new (in Postiz → never sent again; not in Postiz → Today).

Platforms keeps a one-line "Who posts" summary with "Open Publishing".

Run dev builds with `DJQ_POSTIZ_OFFLINE=1` too, so the in-process engine's live store stays off.
8. **Snapshots get a third model (`SnapshotContext.postiz`)**: a copy of the seeded sample with Postiz on for five platforms (Facebook Manual, Threads' channel disabled). Existing shots keep their all-Manual look; `r6-*` shots show Postiz.
9. **Limits: TikTok's title (90) is editable next to YouTube's (100)**, since core made it a real default; the other platforms still show "—".

A job closed as error/copyright/rejected/vanished only counts while the post still shows that outcome, so a reset post reads from its route again.
11. **Postiz-held posts are not tasks.** `isActionableNow`, `dueNow`, the Today count, the Next-up card and the menu bar header skip them (Scheduled / Posting / Draft / Sending / To Postiz). The inbox and fallbacks stay manual tasks with every manual action.

13. **Releasing a test-run draft asks first** (it goes public; DJ Queue can't take it back) and is offered on Today, the Posts row, the inspector's new Postiz section, the menu bar and the post context menu. The context menu also gained "Open live post".
14. **Week slot chips show Postiz by glyph, not colour:** a paper plane (scheduled/queued), doc (draft), or the test tube for test-run posts in place of the dot; inbox and fallbacks get an amber dot; the tooltip names the state.
15. **The menu bar gets a quiet "Postiz today" block** (platform · time · chip · its one action) instead of mixing Postiz posts into "Also due".
16. **"© Blocked" carries no extra © icon** (the text has it).
17. **F2 cover meaning is one short block under Cover text**, grouped by meaning (Thumbnail · YouTube Shorts / Cover frame · Instagram, TikTok / Platform picks · Facebook, Threads, X) for the platforms the clip posts to; core's `CoverMeaning.detail` is the chip's tooltip.
18. **F1: the YouTube title field shows the effective count** ("99/100" next to the label when the template fills it), an error under the field when a typed title is over 100 (core's `.titleTooLong` keeps the clip in Edit, so Done/Send to Queue can't pass it), and core's `TitleCheck` notice when the template had to shorten it (YouTube 100, TikTok 90). The field's limit is min(Settings, 100).
19. **F6: "Too long for X" always offers both choices**, in the editor's Platforms section ("Trim for X" adds X's lane cut at X's limit, "Skip X") and on the Edit card (the same two fixes; "Trim for X" opens the editor with the lane already added and Platforms in view; "Skip X" is the undoable bulk skip). The editor row then states the result: "X posts its own 1:30 trim · the timeline's X lane" (+ Remove) or "X skipped for this clip" (+ Post on X again); the Post-to chip gets a scissors glyph for an own trim.
20. **`DJQ_TOOLTIP_PROBE=r6`** runs only the round-6 probe cases (sidebar Test run row, disabled Postiz segment, Channel disabled badge, detail chevron) so they can be re-run quickly.
21. **Review H1: anything that can make posts public asks first** (the undo toast stays after the confirm): Test run on → off ("From now on, new posts go out publicly …; posts already in Postiz keep their test settings"), Manual → Postiz while Test run is off (count + next slot; "a post whose time has passed goes out within minutes"), and TikTok inbox → Post directly / YouTube → Public on a Postiz platform. The safer directions apply at once. With Settings open the confirm is the modal's own dialog (`AppModel.confirmHere`).
22. **Review H2: a routed post with no job past its slot (or overdue) is "Fell back to manual"**, never held, so its manual row, actions and counts return (to be replaced by core's `displayState`).
23. **Review H3: dev runs (DJQ_HOME or DJQ_ROOT set) are fake by default** — in-memory key, sample transport and `PostizLive.disabled` — unless `DJQ_POSTIZ_LIVE=1`.

## v0.7.1

1. **Tooltip probe misses on grid badges (cases 11/22/33) were the probe, not the app:** SwiftUI hover keeps following the real cursor even in the click-through probe window. A posted move got SwiftUI's hover-in for the badge (so the probe didn't forward it), then the tile turning hot changed the view tree, SwiftUI re-checked hover against Eric's resting cursor and sent hover-out, and the bubble never opened. It depended on where the real cursor rested, not on release vs debug. Fix: in evidence runs, `DSTooltipController.swiftUIHover` drops SwiftUI hover events that disagree with the probe's pointer (counted as "real-cursor hovers dropped"), and every posted move is reconciled with the triggers under the point. New case 8b hovers the score and length badges over a playing Library preview (real proxy, video frame drawn) and fails if a player view is over the badge at its centre (`coveringView`), so z-order is still checked.

- **v0.7.2: proxy-order test waits for the whole queue.** `engineTickOnlyEnqueuesProxies` failed once in the v0.7.1 gate: the background worker can pick up the first queued clip before the tick has queued the rest, so "clips to score first" raced. The test now holds background work (`shouldPause`) until the tick returns. Test-only; app behaviour unchanged.
