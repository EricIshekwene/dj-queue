# Round 4 — auto-update decisions (S5, v0.6.0)

Eric delegated the details; each line is a call made during the build, with why. Eric can change any of them.

1. **Watch only `main` of the source checkout** (default `~/code/dj-queue`, `djq autoupdate on --repo/--branch` to change). A LaunchAgent (`com.djlovd.queue.autoupdate`) has WatchPaths on `refs/heads/main`, its folder, `packed-refs` and `refs/tags`, plus the app's request and window files. Worktrees and task branches never trigger it. *Why:* only merged work ships; launchd is already how the engine runs.
2. **Debounce = 20 s after a commit trigger + launchd's 30 s ThrottleInterval; a run re-reads main before it ends.** A burst of commits costs at most one extra pass, never a queue of runs. *Why:* merges are usually followed by a tag within seconds.
3. **A flock on `autoupdate/run.lock` serialises runs** (watcher, launch check and `djq autoupdate run` alike). A second run while one is going just says so; the running one picks up the newest commit and any request before it ends.
4. **Docs-only = every path changed since the installed build is `*.md` or under `design/`, `docs/`, `refs/`, `screenshots/`.** Judged on the whole range since the installed commit, not one commit, so a docs commit after a code commit still installs the code. Skipped runs are logged. A docs-only result also clears a block whose commit it contains (main is back to installed code).
5. **The gate runs in a scratch clone of the local repo** (`<app support>/autoupdate/work`, checked out detached at the exact commit, `git clean -ffdx` except `.build` so incremental builds stay fast). It runs `scripts/test.sh` then `scripts/build-app.sh` with scratch `DJQ_HOME`/`DJQ_ROOT`, `DJQ_NOTIFY=0` and every other `DJQ_*` variable removed. *Why:* never Eric's working tree, never the real database; the cache keeps a gate to a few minutes.
6. **No GitHub access.** The watcher clones/fetches from the local checkout only; it never pushes, pulls or fetches remotes.
7. **Build warnings don't block; failing tests or a failed build do.** The block reason names the failing tests (or the first compiler error); `djq autoupdate log --run` shows the full output. *Why:* the gate protects Eric's data and app, not code style; the 0-warning rule stays a review rule for sessions.
8. **Install is done by the runner, mirroring `build-app.sh --install`:** move the installed bundle to `autoupdate/previous/`, move the gated bundle in, relink `~/bin/djq`. `build-app.sh --install` now also keeps the replaced bundle there, so manual installs can be rolled back too. *Why:* a gated build can wait for the window to close and install later without rebuilding.
9. **Before installing: wait for the engine to be idle** = no post in state `rendering` (posting is manual, so there's no in-flight post to protect). Waits up to 2 h, then leaves the build ready for the next trigger.
10. **Backup before every install** to `autoupdate/backups/queue-before-<version>-<time>.sqlite` (SQLite backup API + `integrity_check`); keeps the 10 newest plus any a rollback still needs. A failed backup means nothing installs.
11. **Verify = same clip ids, scores, titles and count** (from `djq videos --state all --json` of the old and new builds) **+ no *new* Doctor errors** (errors that were already there before the install don't count; auto-update's own findings never count) **+ the installed version matches the build.** *Why:* a pre-existing Doctor error (say, a missing source file) must not block every future update.
12. **A failed verify rolls back to the kept bundle and restarts the engine.** If the new build migrated the database, the pre-install backup is restored too, but only when no post changed since the backup; otherwise the new build stays installed, the update is marked failed and `djq autoupdate rollback --restore-db` is offered. *Why:* restoring over newer post history could cause a double post.
13. **`djq autoupdate rollback` swaps the installed and kept builds** (a second rollback rolls forward). Refused when the installed build migrated the database unless `--restore-db` also restores the backup taken before it; the message names the backup and how many post changes would be lost. The rolled-back commit isn't reinstalled; the next commit installs as usual. Rolling back to a build without auto-update turns the watcher off and says so.
14. **Window in use = the app's main window is open in a live process** (the app writes `window.json` on open/close). Then the build waits as "Update ready"; closing the window installs it (that's also what "Later" does — Later only changes the wording and hides the banner). "Restart & update" asks the runner to install now; the engine restarts with the app (`launchctl kickstart -k`), and the relaunched app reopens its window.
15. **Notifications come from the app, not the runner.** The runner records notices in `state.json`; the app delivers each once (the CLI has no notification rights).
16. **Default on; posting untouched.** The v0.6.0 install turns auto-update on for Eric's install (`djq autoupdate on`). Install, verify and rollback never change Settings, so paused posting stays paused.
17. **Doctor `autoupdate` checks stay silent until auto-update is set up** (config file exists): `autoupdate.watcher` (warning: on but not loaded), `autoupdate.blocked` (warning), `autoupdate.failed` (warning), `autoupdate.ready` (info: waiting > 24 h), `autoupdate.off` (info). None is an error, so they can never fail an update's own verify.
18. **Every installed bundle carries its commit** (`DJQGitCommit` in Info.plist, stamped by `build-app.sh`), so "What's new" and "is this new?" never guess. Older bundles fall back to the recorded state or the version tag.
19. **A new tag on an already-installed commit rebuilds it** (version label changes, e.g. 0.6.0-dev.2 → 0.6.0); the code is the same, so it's quick and verified like any update.
20. **Dev runs:** `DJQ_APP_DIR`, `DJQ_BIN_DIR`, `DJQ_AUTOUPDATE_REPO` redirect the installed app, the `djq` link and the watched repo; with `DJQ_HOME`/`DJQ_ROOT` set the watcher refuses to install and the engine is never kickstarted. `DJQ_AUTOUPDATE_FAIL_VERIFY=1` forces a verify failure (rollback test).
